# crossmarket-agent

Мультитул-агент для сравнения цен между маркетплейсами (Wildberries ↔ Озон):
поиск товара по описанию, матчинг карточек между площадками, аналитика цен —
плюс eval-харнесс и observability вокруг всего этого.

## Что уже работает

- **Снапшот корпуса**, собранный полуручно браузерным скрапером: цены и
  атрибуты в ClickHouse, тексты в Qdrant, эмбеддер
  `intfloat/multilingual-e5-large` локально.
- **Tool A: Retrieval-QA** — агент на Claude Agent SDK с одним тулом поверх
  Qdrant + ClickHouse. Отвечает по снапшоту или честно говорит, что товара в
  базе нет.
- **Tool C: text2sql** — агент пишет настоящий SQL к снапшоту в ClickHouse и
  чинит его по тексту ошибки. Знание о схеме, диалекте и ловушках данных вынесено
  в skill Claude Agent SDK, а не вклеено в промпт.
- **Tool B: матчинг ВБ ↔ Озон** — карточка Wildberries → кандидаты из озон-коллекции
  → текстовая модель подтверждения по каждому. Ни один не подтверждён — возвращается
  пусто: похожий товар за найденный не выдаётся.
- **Роутинг A + B + C** — одна конфигурация со всеми тулами: оркестратор сам решает,
  доставать ответ из текста карточки, искать товар на второй площадке или считать
  по базе.
- **Eval-харнесс**: `make eval` — recall@k и MRR на golden-set, end-to-end прогон
  агента с метриками по итоговому ответу, точность text2sql по строкам результата,
  accuracy роутинга; отчёты в `evals/reports/`, метрики в MLflow, трейсы в Langfuse.
  Golden-set разбит на калибровочную и отложенную части до появления судей;
  отчётные цифры — только с отложенной.
- **Судьи** — три LLM-судьи: итоговый ответ агента, вердикт матчера, SQL агента.
  Промпт доводится на калибровочной части, отчётная цифра согласия с истиной — с
  отложенной, рядом с ней всегда baseline судьи, отвечающего одинаково на всё, и
  бесплатная детерминированная проверка.

## Цифры

Отложенный тест-сплит, 24 вопроса из 61, корпус 884 карточки:

| | opus-5 | haiku-4.5 |
|---|---|---|
| верный исход | 1.000 | 0.833 |
| релевантная карточка названа в ответе | 1.000 | 0.636 |
| цены и товары из ответа подтверждены выдачей поиска | 1.000 | 1.000 |
| стоимость вопроса | $0.060 | $0.020 |

Голый retrieval без агента, тот же сплит: recall@1 0.682, recall@5 0.818, MRR 0.783.

Отрицательных вопросов в наборе 33 — тех, ответа на которые в корпусе нет. Opus
отказал верно на всех, включая близкие промахи, где рядом в корпусе лежит похожий
товар.

Вторая модель показывает, чем платит дешёвая: все провалы haiku — «не пошёл искать»,
ни одного «искал и выбрал не то». Из 28 вопросов с ответом в корпусе он вызвал поиск
на 21 и во всех 21 назвал все релевантные карточки, остальные семь не стал искать.
Выдуманных цен и товаров нет ни у одной модели.

### Матчинг ВБ ↔ Озон

Отложенный тест-сплит, 61 размеченная пара, среднее трёх прогонов:

| | значение |
|---|---|
| F1 | 0.747 |
| precision / recall | 0.862 / 0.660 |
| «аналога нет»: доля товаров, где ни один чужой кандидат не подтверждён | 1.000 |
| настоящий партнёр дошёл до модели подтверждения | 1.000 |

Слабое место проекта — и по построению замера видно, где именно: кандидатов
retrieval достаёт без потерь, теряется треть пар на шаге подтверждения, потому что в
карточке часто нет признака, по которому пару можно отождествить. Разбор —
[docs/findings.md](docs/findings.md).

Точность text2sql на эталонных кейсах — 0.947, accuracy роутинга между тремя тулами —
1.000; обе цифры с отложенных сплитов.

### Судьи

Согласие судьи с истиной на отложенных сплитах. Положительный класс — «плохо»:
precision — доля настоящих ошибок среди объявленных судьёй, recall — доля пойманных.

| судья | что судит | истина | тест | согласие | baseline | precision | recall |
|---|---|---|---|---|---|---|---|
| QA | итоговый ответ агента | ручная разметка | 17 | 0.941 | 0.765 | 0.800 | 1.000 |
| B | вердикт модели подтверждения | метка пары | 61 | 0.770 | 0.656 | 0.769 | 0.476 |
| C | SQL агента и его ответ | эталонный запрос | 76 | 0.882 | 0.908 | 0.000 | 0.000 |

`baseline` — согласие судьи, отвечающего одинаково на всё. Без этой колонки все три
цифры читались бы как успех; с ней видно, что судья C проигрывает вырожденному.

Разбор расхождений:

| судья | где ошибается | почему |
|---|---|---|
| B | не ловит ни одного из 5 ложных подтверждений | пара с одним спрятанным отличием: судья видит те же карточки, что тул, и не находит его там же |
| B | пропускает 6 из 16 ложных отказов | в выгрузке нет признака, по которому разметчик отождествил пару; opus вместо sonnet не помогает |
| C | не ловит ни одного из 7 промахов | промах text2sql — правдоподобный запрос с не тем результатом; без исполнения неотличим от верного |
| C | 9 ложных тревог | часть — разные определения: судья оценивает текст ответа, метрика — результат запроса |
| QA | 1 ложная тревога на тесте | придирка к тому, как агент прочёл характеристики карточки |

Итог: прямые метрики первичны. Там, где эталон есть, судья проверяет себя об него — C
проверку проваливает, B работает на половине ошибок, судья ответов сыграл вничью с
проверкой по словам (0.925 у обоих на всех 40 размеченных). Подробно —
[docs/findings.md](docs/findings.md), отчёты — `evals/reports/judge_*.md`.

Короткие выводы по всем замерам — [docs/findings.md](docs/findings.md), лог факапов —
[docs/failures.md](docs/failures.md), отчёты прогонов — [evals/reports/](evals/reports/).

**Воспроизвести из клона нельзя: данных в репозитории нет** — ни корпуса, ни фона из
700 дистракторов. Решение осознанное: в гит идут только golden-set и отчёты прогонов.
